# 高标准 AI Agent / LLM 应用开发流程基准清单

这是复盘时的对照基准。按阶段排列，每个环节都标注了"专业开发者会做什么"和"初学者常见缺失"。复盘时逐项打标。

---

## 阶段 1：需求与目标定义

| 环节 | 专业开发者会做什么 | 初学者常见情况 |
|---|---|---|
| 1.1 问题定义 | 写清楚这个Agent解决谁的什么问题，输入输出是什么 | 直接说"帮我做个XX"，没有边界 |
| 1.2 成功指标 | 定义"做完了算好"的标准（准确率？响应时间？用户满意度？） | 没有指标，跑通就行 |
| 1.3 约束条件 | 明确预算、延迟要求、数据隐私红线、交付时间 | 从未考虑 |
| 1.4 可行性判断 | 评估这个问题真的需要LLM吗？规则引擎/搜索/简单脚本能不能搞定？成本差异？ | 上来就用大模型 |
| 1.5 竞品/方案调研 | 看看有没有现成产品/开源项目可以直接用，避免重复造轮子 | 直接开写 |

**典型AI补丁信号**：AI在实现中才开始追问"你这个具体要干嘛？"——说明需求没定义清楚。

---

## 阶段 2：架构与技术选型

| 环节 | 专业开发者会做什么 | 初学者常见情况 |
|---|---|---|
| 2.1 Agent架构决策 | 想清楚：单Agent？多Agent协作？还是固定流程的Pipeline？为什么？ | 没想过，AI给什么用什么 |
| 2.2 LLM模型选型 | 比较GPT-4o/Claude/开源模型的能力、价格、速度、上下文长度，根据场景选 | AI默认用某个模型，用户没概念 |
| 2.3 开发框架选择 | 评估LangChain/LangGraph/CrewAI/AutoGen/纯API调用的利弊，选最合适的 | AI直接装了LangChain，用户不知道为什么 |
| 2.4 知识方案决策 | RAG vs 微调 vs Few-shot vs 纯Prompt，根据数据量和更新频率选 | 没想过，AI决定 |
| 2.5 工具/Function设计 | 列出Agent需要调用哪些外部工具，每个工具的输入输出schema | AI在代码里随手加了几个工具调用，用户没设计过 |
| 2.6 记忆系统设计 | 短期对话记忆？长期用户画像？检索记忆？怎么存怎么取？ | 完全没考虑记忆问题 |
| 2.7 状态管理 | 多轮对话/多步任务中状态怎么维护？ | AI用了全局变量或字典，用户没意识到这是个设计决策 |

**典型AI补丁信号**：`pip install langchain` 出现在项目里，但对话中从没讨论过"为什么用框架"。

---

## 阶段 3：数据与知识准备

| 环节 | 专业开发者会做什么 | 初学者常见情况 |
|---|---|---|
| 3.1 数据源识别 | 明确需要哪些数据喂给Agent | 有啥用啥 |
| 3.2 数据清洗 | 去重、去噪、格式化处理 | 直接扔进去 |
| 3.3 切分策略 | 文档chunking怎么切？按段落？按token？重叠多少？ | AI用了默认切分，用户不知道这是可调参数 |
| 3.4 Embedding模型 | 选OpenAI embeddings还是开源模型？中文效果如何？ | 用默认值 |
| 3.5 向量库选型 | Chroma/Pinecone/FAISS/PGVector，根据规模和部署方式选 | AI选了Chroma，用户不知道有其他选择 |
| 3.6 检索策略 | 纯向量检索？关键词混合？Rerank？Top-K设多少？ | 用默认 |

---

## 阶段 4：开发实现

| 环节 | 专业开发者会做什么 | 初学者常见情况 |
|---|---|---|
| 4.1 环境搭建 | Python版本、虚拟环境、依赖锁定（requirements.txt/poetry） | AI建了个venv，用户没管 |
| 4.2 项目结构 | 模块化目录组织（src/、config/、prompts/、tools/） | 一个main.py从头写到尾 |
| 4.3 Prompt管理 | Prompt模板独立维护、版本管理、变量化 | 硬编码在代码字符串里 |
| 4.4 错误处理 | LLM调用失败怎么办？工具调用失败怎么办？超时怎么办？重试？降级？ | 没有try/except，崩了才加 |
| 4.5 配置管理 | API Key、模型名、参数通过环境变量/配置文件管理 | Key硬编码在代码里 |
| 4.6 日志 | 记录每轮LLM调用的prompt、response、耗时、token消耗 | 没有日志 |
| 4.7 速率限制/重试 | 处理API rate limit、网络抖动 | 遇到了才加 |

**典型AI补丁信号**：代码里出现了 `try/except`、`os.getenv()`、`logging`、`requirements.txt`——这些都是用户没要求但AI认为该有的。

---

## 阶段 5：测试与评估

| 环节 | 专业开发者会做什么 | 初学者常见情况 |
|---|---|---|
| 5.1 评估集构建 | 准备10-50个典型测试case，包含正常和边界情况 | 没有测试集 |
| 5.2 端到端测试 | 跑通完整流程，验证输出是否符合预期 | 手动点几次觉得行了 |
| 5.3 边界/失败case | 测试恶意输入、超长输入、空输入、不相关输入 | 没测过 |
| 5.4 幻觉检测 | 检查Agent是否编造信息、引用不存在的来源 | 没考虑过 |
| 5.5 性能测量 | 实际延迟多少？token消耗多少？单次调用成本多少？ | 没算过 |
| 5.6 安全测试 | Prompt注入？越权调用工具？敏感信息泄露？ | 完全没考虑 |
| 5.7 回归验证 | 改了Prompt或代码后，旧测试case是否还过 | 改完直接用 |

**这是初学者最常完全跳过的阶段。**

| 环节 | 专业开发者会做什么 | 初学者常见情况 |
|---|---|---|

## 快速对照速查

如果项目里出现了以下情况，说明对应环节是AI打的补丁：

- 出现 `langchain` / `llamaindex` / `crewai` 但没讨论过框架选择
- 出现 `requirements.txt` / `pyproject.toml` / `venv` 但用户没提过依赖管理
- 出现 `.env` / `os.getenv()` / `config.py` 但用户没提过配置
- 出现 `try/except` / `retry` / `timeout` 但用户没要求错误处理
- 出现 `logging` / logger 对象但用户没要求日志
- 出现分目录结构（src/ tools/ prompts/）但用户没要求工程化
- 出现测试文件（test_*.py）但用户没要求测试
- 出现 `.gitignore` / git 提交但用户没提过版本管理
- 出现 Dockerfile / docker-compose 但用户没提过部署
- 最终效果"能用但说不清楚为什么这么设计"
